# CashSense Premium verification review

Reviewed November 15, 2026. Evidence: the uploaded `CashSense-AWS-Project-20261115-173048-852640.zip`, account 781540302423, us-east-1. All 372 files in its checksum manifest matched. The archive includes 26 Lambda deployments, three HTTP APIs and their routes/integrations, IAM policies and table schemas. The two export warnings concern absent optional resource policies on AppleTestNotification and PushSender; neither blocks this billing review.

## Conclusion

The exported production configuration does not provide a complete, working store-verified Premium lifecycle. Staging has newer code, but production does not use it. Nothing in AWS was changed during this review. The uploaded export is a snapshot; later AWS changes are outside this assessment.

## Prepared corrections

Eight deployment ZIPs accompany this report. Billing, Users and both store notification handlers share the reconciler and strict authorization policy. RegisterDevice and all three backup functions use that same pure authorization policy rather than cached tiers/booleans. Existing device/backup operations and deployed dependencies are retained.

Ordinary access requires a server-created entitlement entry with storeVerified=true, a supported store, and a future Unix-seconds expiry. Only successful store reconciliation writes that marker. Existing developer/tester flags remain explicit exceptions, as previously requested. Standalone trial dates no longer grant access; a trial verified as an active store subscription uses the store entitlement normally. Paid cancellation retains access through store-reported expiry. Expiration/revocation clears that claim and falls back to another verified purchase. Notifications re-fetch current store status instead of trusting event order.

A production API change plan and IAM additions are in config/. The legacy /billing/verify and /entitlements/refresh routes can target Billing; requests must contain productId and exactly one of transactionId or purchaseToken. Older clients that omit productId need a client update. No caller-supplied Premium flag is accepted.

## Required rollout and migration

1. Validate the eight ZIPs against isolated staging functions and tables. Keep the existing production and staging APIs separate. The provided policy and route plan reference production only as a review plan; no automatic deployment script is included.
2. Confirm actual store product IDs, bundle/package IDs, Apple numeric app ID, secret references and Google Pub/Sub audience/email. Exported environment values were redacted, so this review confirms key presence only. Do not replace real environment values with [REDACTED] or the explanatory config placeholders.
3. Add the exact DynamoDB actions in config/production-role-additions.json and preserve existing operational permissions. Billing needs Claims Scan for reconciliation; AppleNotifications needs Claims PutItem. AWS transactional writes use the item-level PutItem/UpdateItem permissions. If secrets use a customer-managed KMS key, assess its decrypt permissions separately.
4. Use Node.js 24 and index.handler. Suggested settings: Billing 512 MB/300 seconds for maintenance pages, notification functions 512 MB/120 seconds, Users 128 MB/15 seconds. API Gateway requests still have their own integration deadline; retries must remain idempotent. Keep backups/device settings unless staging measurements require changes.
5. Apply config/production-route-plan.json, preserve the existing JWT authorizer, and add narrowly scoped API Gateway invoke permissions on each new/repointed Lambda route. Main Apple webhook must target CashSense-AppleNotifications; the old AppStoreNotificationsV2 and EntitlementsRefresh functions must have no remaining public entitlement-writing route. No deletion of those legacy functions is required for the planned cutover.
6. Deploy all eight candidates as one coordinated rollout AFTER staging and migration checks. Enable Apple V2 notifications and authenticated Google RTDN in the actual store consoles. Store console settings and Google Pub/Sub configuration are not in this AWS export.
7. Install the paginated reconciliation workflow from config/reconciliation.asl.json, substitute the actual Billing ARN and schedule it every 15 minutes with an appropriate Step Functions execution role. Alert on nonempty per-claim failures as well as workflow errors. Workflow success alone is not proof that all claims refreshed.
8. Reverify existing purchases before enforcing the new policy for paying users. Old summaries and old ledger entries lack the new storeVerified marker, so they are intentionally denied by the candidate until reverified. Perform a server sweep where saved tokens/transaction IDs exist; otherwise use authenticated Restore Purchases on the original store platform. A hashed Google claim cannot recover its purchase token. The export contains no customer records, so no real accounts were migrated or classified here. Do not mark old records as verified just to avoid this migration.
9. Ensure the installed Flutter build uses mandatory Apple/Google AWS verification, refreshes membership from /users/me on launch/resume/purchase/restore/account switch, and does not unlock from local backup/lastPurchase/promo values. The GitHub main billing file read earlier in this session contained those bypasses; the uploaded AWS ZIP does not include the installed Flutter source. Backend candidates alone cannot certify client UI behavior.
10. Run real Apple Sandbox/TestFlight and Google license-test purchases through verification, renewals, cancellation, expiry, refunds, grace/hold, duplicate/out-of-order webhooks, ownership conflicts, cross-store fallback and all Premium backup endpoints. Compare API responses and DynamoDB updates. Preserve production user financial data throughout.

## Validation and limits

58 offline tests pass with zero failures. All eight candidate packages passed ZIP CRC and JavaScript syntax checks. Four billing handlers passed offline import checks with bundled dependencies. The four device/backup candidates preserve deployed dependencies and were syntax checked; their shared Premium policy was exercised separately. Their full SNS/S3 operations were not executed.

Tests use mocked store SDK responses and in-memory DynamoDB behavior. They do not validate real signature chains, store credentials, AWS IAM execution, DynamoDB expression parsing, actual notifications or installed Flutter behavior. No production deployment, real purchase, customer row read, or store secret retrieval occurred. The review demonstrates code/configuration defects and prepares testable corrections; it does not certify production billing as fixed.

The candidate retains verified Apple Sandbox support for staging/TestFlight. Sandbox verification is not evidence of a paid production transaction. Enforce environment separation if that distinction is required by your release policy. Missed Google one-time refunds outside the store's available void-history window require separate store audit evidence.
